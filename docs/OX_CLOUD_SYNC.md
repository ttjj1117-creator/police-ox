# OX 문제·학습 기록 동기화

2026-10-24. 기존 OX 형식과 ID를 유지하면서 같은 계정의 PC와 갤탭에서 문제은행·완료한 풀이·다시 보기를 공유한다. 원문 객관식과 OX는 로그인만 공유하며 문제은행, 응답, 통계, 전송 대기열과 서버 버전은 별도로 관리한다.

## 보존 범위

| 자료 | 처리 |
|---|---|
| OX 실제 학습 문제은행 | `datasetId`, 문항·목차·학습 단원 ID와 각 버전을 유지하여 공유 |
| 출제 당시/현행 판단 | `basis=exam/current`, `itemRevision`, `judgmentRevision`을 응답·문항 스냅샷과 함께 보존 |
| 완료·종료한 학습 | 세션과 해당 응답을 한 묶음으로 전달. 원래 ID·시각·정오 결과 유지 |
| 다시 보기 | 문항 ID와 판단 기준의 쌍으로 분리. 설정·해제 모두 버전 이력 유지 |
| 삭제된 지문 | 삭제 이력으로 오래된 기기의 자동 복원을 막음. 과거 세션의 스냅샷·응답은 보존 |
| 진행 중 세션·답안·현재 위치 | 시작한 기기에 유지. 완료/종료 전에는 다른 기기의 활성 세션으로 보내지 않음 |
| 순회 잔여 목록·균형 배정·글자 크기 | 기기별 유지 |
| 로그인 전 OX·시연 자료 | 기존 로컬 저장 영역 유지. 로그인만으로 자동 업로드하지 않음 |
| 원문 객관식 자료와 통계 | 기존 원문 동기화 경로에 유지. OX와 합산하지 않음 |

새 URL에 접속하거나 소스 파일을 복사하는 일은 기존 IndexedDB 기록을 옮기는 작업이 아니다. localhost와 GitHub Pages는 서로 다른 저장소다. 이전 PC 기록은 전체 백업과 미리보기로 연결한다. 원본 백업과 로그인 전 로컬 기록을 삭제할 필요가 없다.

## 계정과 로컬 저장

원문 앱의 공통 로그인 화면에서 사용 중인 Supabase 프로젝트·계정을 사용한다. 공개 연결값만 프런트엔드에 제공하며 DB 비밀번호나 관리자 키를 사용하지 않는다. 이메일 로그인 링크는 앱에서 인증을 검증한 뒤 공통 세션으로 보관한다. OX 계정은 프로젝트 URL과 사용자 ID를 함께 기준으로 분리한다.

계정의 OX 상태와 그 변경의 전송 대기열은 하나의 IndexedDB transaction으로 저장한다. 어느 쪽 저장이 실패해도 둘 다 반영하지 않는다. 서버 수신 확인을 저장하기 전에는 대기열을 버리지 않는다. 서버가 이미 받은 뒤 응답이 끊어지면 같은 `eventId`로 재시도한다. 계정 전환·로그아웃 시 이전 계정의 로컬 캐시와 미전송 기록은 해당 계정 영역에 남으며 다른 계정으로 전송하지 않는다.

로그인 전의 기존 `real`/`demo` OX 저장 키와 원문 저장 영역을 삭제하지 않는다. 계정 상태는 `ox:real:user:<프로젝트URL|사용자ID>`, 대기열·커서는 `ox-sync:real:user:<프로젝트URL|사용자ID>`에 분리한다. 기존 기록 연결은 사용자가 지문·종료 세션·응답·충돌 수를 미리보고 실행한다. 연결에 사용한 원본 백업은 `ox-sync:migration-source:<소유자>`에 함께 보관한다. 같은 백업의 같은 ID·내용은 중복 생성하지 않으며 같은 ID의 다른 내용은 자동 덮어쓰지 않는다. 가져올 백업이나 현재 계정에 진행 중 세션이 있으면 먼저 기존 기기에서 완료/종료하도록 안내한다. 진행 중 기록을 제외하고 임의로 일부만 이전하지 않는다.

지원하는 파일은 `backupSchemaVersion:1` OX 전체 백업 또는 `format:"police-learning-backup"`, `namespace:"real"` 통합 백업의 `ox`에 담긴 같은 OX 전체 백업이다. 원문 문제 데이터 파일이나 문제만 내보낸 파일은 OX 응답 이전에 쓰지 않는다.

## 서버 계약과 권한

새 마이그레이션은 `supabase/migrations/202610230002_ox_sync.sql`이다. 기존 원문 테이블·함수·버킷을 대체하지 않는다.

| 서버 객체 | 용도 |
|---|---|
| `police_ox_sync_heads` | 사용자별 OX cursor·문제은행 CAS 버전 |
| `police_ox_sync_events` | 변경 불가능한 OX 이벤트 로그. 사용자·eventId, 사용자·deviceId·deviceSequence, 사용자·seq 고유 제약 |
| `police_ox_sync_marks` | 사용자·문항/판단 기준별 다시 보기 버전. 해제도 보존 |
| `police-ox-sync-private` | 비공개 본문 객체. 경로 `<인증 사용자 UUID>/ox/objects/<SHA-256>` |

```text
police_ox_sync_push(p_event: WireEvent)
  -> { seq, bankVersion, markVersion, duplicate, serverTime }

police_ox_sync_pull(p_after: bigint, p_limit: 1..100)
  -> { events: [{ seq, bankVersion, markVersion, event: WireEvent }],
       cursor, bankVersion, serverTime }
```

wire 형식은 `protocolVersion=1`, `eventId`, `deviceId`, `deviceSequence`, `baseCursor`, `createdAt`, `kind`, `bodyPath`, `bodySha256`, `bodyBytes`, `baseVersion`, `markQuestionId`, `baseMarkVersion`이다. 이벤트 종류는 `bank`, `session`, `mark`, `resolution`이다. 다시 보기 키는 기존 `JSON.stringify([itemId,basis])`를 유지한다. 긴 기존 ID가 PostgreSQL 인덱스 크기 제한에 걸리지 않도록 서버 인덱스에는 고정 길이 digest를 사용하되 원래 키도 저장·대조한다. digest가 충돌해도 다른 문항의 표시를 덮어쓰지 않는다.

서버는 요청이 보낸 사용자 ID를 믿지 않고 `auth.uid()`에서 소유자를 구한다. 모든 OX 테이블에 소유권 RLS를 적용하며 authenticated 직접 INSERT/UPDATE/DELETE 권한은 주지 않는다. 쓰기는 빈 `search_path`를 가진 `SECURITY DEFINER` RPC만 수행한다. 익명 RPC 실행 권한은 없다. RPC는 사용자별 head 행을 잠가 버전과 cursor 변경을 직렬화한다.

같은 `eventId`와 같은 내용은 처음과 같은 수신 확인을 반환한다. 같은 ID의 다른 내용이나 같은 기기 순번의 다른 이벤트는 거부한다. 문제은행의 `baseVersion`, 다시 보기의 `baseMarkVersion`이 오래되면 자동 덮어쓰지 않는다. 앞선 문제은행 변경이나 같은 문항/판단 기준의 표시 변경이 충돌하면 그것에 의존한 뒤의 대기 변경도 자동 전송하지 않는다. 사용자가 다른 기기의 최신 자료와 보관된 각 변경을 확인한 뒤 명시적으로 다시 반영한다. 첫 충돌을 해결했다고 뒤의 오래된 변경까지 한꺼번에 승인하지 않는다.

Storage는 사용자 경로와 `ox` namespace를 모두 확인한다. OX RPC는 OX 버킷에서만 본문을 찾으며 원문 `/real/` 경로나 원문 버킷의 객체를 참조하지 않는다. 원문 RPC도 OX 경로를 받지 않는다. 같은 인증 사용자가 양쪽 앱을 사용하는 것은 허용하며 서로 다른 클라이언트 종류를 보안 경계로 가정하지 않는다. restrictive Storage 정책으로 기존의 넓은 permissive 정책이 있어도 OX 객체의 타 계정 접근·덮어쓰기·삭제를 막는다.

한 Storage 객체와 manifest의 제한은 1 MiB다. 논리 이벤트는 최대 100 MiB이며 256 KiB 조각으로 나눈다. 수신 시 경로·크기·SHA-256, manifest와 이벤트의 ID·버전 일치, OX 데이터·백업 계약을 검증한 뒤 반영한다. 불완전한 다운로드가 현재 정상 문제은행과 기록을 지우지 않는다. 로그인·개인 API 응답을 공용 PWA 캐시에 넣지 않는다.

## 동시 학습과 오프라인

완료한 기록의 도착 시각으로 원래 `answeredAt`을 바꾸지 않는다. 같은 기기는 저장 순서, 다른 기기는 관찰한 서버 cursor와 유효한 시계 보정을 사용한다. 교차 기기 응답의 선후를 확정할 수 없으면 원본 응답을 모두 보존하고 대표 상태 확인을 요청한다. 사용자가 실제 후보 응답을 선택하면 별도 resolution 이벤트로 공유한다. 판단 기준과 판단 버전이 다른 기록을 현재 정오 상태에 섞지 않는다.

진행 중 OX 학습이 있을 때 받은 원격 문제은행·기록은 보류한다. 현재 문항 스냅샷과 답안 위치를 바꾸지 않으며 학습이 끝난 뒤 검증해 반영한다. 문제은행 버전 충돌, 같은 ID의 다른 세션·응답과 불확실한 응답 순서는 확인 대상으로 보관한다. 두 원본 중 정답을 자동으로 고르거나 오래된 문제은행으로 전체 기록을 교체하지 않는다.

답안은 먼저 이 기기에 저장한다. 완료/종료 뒤 전송 대기열에 보관하고, 앱을 열어 둔 상태에서 연결이 돌아오거나 앱을 다시 실행하면 재시도한다. 브라우저를 완전히 닫은 동안의 백그라운드 전송을 보장하지 않는다. `지금 동기화` 후 `동기화 완료`·전송 대기 0건·확인 필요 건수를 확인한다. 다운로드를 마친 문제를 오프라인에서 사용할 수 있으며 최초 다운로드와 로그인에는 인터넷이 필요하다.

문제가 생기면 `OX 전체 백업 내보내기`와 `OX 대기열·충돌 복구 파일`을 먼저 보관한다. 백업 전체 교체와 기존 기록의 계정 연결은 구분한다. 계정 연결은 검증된 병합이며 빈 백업이나 일부 문항 파일로 클라우드 전체를 초기화하지 않는다.

## 검증 범위

`supabase/ox-rls-tests.sql`에는 두 가상 계정, 익명 접근 거부, 재시도·CAS·불변 객체, 원문/OX 분리, 긴 ID를 확인하는 **54개 fail-fast pgTAP assertion**을 준비했다. 끝의 `ROLLBACK`으로 테스트 사용자와 메타데이터를 남기지 않는다. SQL Editor가 마지막 결과만 표시하더라도 앞선 실패가 감춰지지 않도록 assertion이 실패하면 예외를 발생시킨다. Storage fixture는 메타데이터이므로 실제 바이트 업로드·다운로드의 증거와 구분한다.

실행 예시: 두 마이그레이션을 설치한 테스트 DB에서 `psql -v ON_ERROR_STOP=1 -f supabase/ox-rls-tests.sql`을 실행하거나 SQL Editor에서 파일 전체를 실행한다. 운영 DB에서 실행하려면 가상 UUID가 기존 사용자와 겹치지 않는지 확인하고 전체 transaction을 유지한다. 실제 서버 적용·실제 계정 전송·배포 및 자동 테스트 결과는 해당 작업의 최종 검증 기록을 따른다. 이 문서의 준비된 검사를 실제 통과한 결과로 간주하지 않는다.

이전 순서는 [OX PC→갤탭 이전](OX_PC_TO_TABLET_MIGRATION.md)을 따른다.
