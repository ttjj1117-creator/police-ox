# 원문 학습 동기화 계약

이 문서는 구현한 프로토콜과 로컬 저장 경계를 설명한다. 실제 서버 설치·RLS 검증 결과와 메일·배포의 남은 확인은 [실서비스 검증](LIVE_CONNECTION_VERIFICATION.md)을 따른다. 원문 교환 계약 `police-original-questions / 1.0.0`, 기존 문항 ID·단원 코드·OX 데이터 형식은 변경하지 않는다.

## 이메일 로그인 링크와 인증번호

현재 Free 기본 메일의 로그인 링크를 지원하며, OTP 템플릿이 있는 프로젝트는 기존 인증번호 입력도 유지한다. 인증 fragment는 controller 모듈 평가 시 IO보다 먼저 메모리로만 캡처하고 URL에서 제거한다. 정상·오류 모두 원문 real의 동기화 화면으로 진입한다. JWT의 issuer·subject·만료 구조 확인은 힌트 검증이며, 설정한 서버 `/auth/v1/user`의 실제 검증과 ID 대조를 통과해야만 인증 정보를 저장한다. 만료·불완전·다른 프로젝트·다른 로그인 계정은 자동 수락하지 않는다.

링크가 비활성 UI를 우회할 수 있으므로 로그인 직전에 저장된 계정과 진행 중 익명 세션을 다시 읽는다. 다른 계정 로그인이나 진행 중 익명 학습을 자동 교체하지 않고, 익명 문제은행·기록도 자동 업로드하지 않는다. 동시 초기화는 하나의 Promise를 공유한다. 사용자 지정 서버 설정은 재시작 뒤에도 유지되고 빌드 환경값은 그 설정이 없을 때 기본값으로 사용한다.

## 동기화 범위

| 자료 | 처리 |
|---|---|
| 원문 real 문제은행·패키지·그림 | 같은 계정의 서버 버전으로 전달 |
| 완료·종료한 일반/회차 학습 | 세션 스냅샷과 확정 응답을 한 묶음으로 전달 |
| 제출·시간 만료 모의고사 | 최종 세션·답안·채점 기록을 한 묶음으로 전달 |
| 중요 표시 | 설정과 해제 모두 버전이 있는 이벤트 |
| 문제·파일 삭제 | 삭제 이력을 유지하여 오래된 기기의 복구를 차단 |
| 진행 중 답안·현재 위치·모의고사 종료 시각 | 시작한 기기에 보관. 다른 기기의 활성 세션으로 전송하지 않음 |
| 글자 크기·배치 | 기기별 유지 |
| OX | 같은 로그인으로 별도 OX 동기화 사용. 원문 문제·통계와 합산하지 않음 |
| demo | 기존 로컬 기능과 백업 유지. 클라우드에 보내지 않음 |

일반 학습 중 이미 확정한 응답은 그 기기의 현황에 즉시 반영된다. 다른 기기에 공유되는 시점은 해당 세션을 완료하거나 종료한 뒤다. 학습 중에는 두 기기의 현황이 잠시 다를 수 있다. 모의고사는 네트워크와 관계없이 저장된 `deadlineAt`으로 만료를 확정한다.

## 로컬 소유권과 원자적 저장

기존 `police-ox-storage`, 버전 1, `states` object store를 함께 사용한다. OX 저장소를 삭제하거나 버전을 올리지 않았다.

| 키 | 의미 |
|---|---|
| `original:real` / `original:demo` | 로그인 전 기존 원문 기록 및 시연 기록 |
| `real` / `demo` | 기존 OX 저장 영역 |
| `original:real:user:<프로젝트URL\|사용자ID>` | 해당 서버·계정의 원문 캐시 |
| `sync:real:user:<프로젝트URL\|사용자ID>` | 해당 계정의 outbox·커서·원래 응답 순서·충돌·시계 보정 |
| `sync:auth:<프로젝트URL>` | 현재 기기의 로그인 세션 |
| `sync:migration-source:<소유자>` | 연결에 사용한 원본 전체 백업 보관 |

로그인만으로 로그인 전의 real 기록을 업로드하지 않는다. 사용자가 미리보기를 확인한 뒤 기존 기록 연결을 실행한다. 연결은 현재 클라우드 문제은행과 가져온 자료의 합집합을 사용한다. 빈 파일이나 일부 회차만 가진 PC가 전체 클라우드를 지우는 명령으로 처리되지 않는다. 서버 삭제 이력이 있는 자료는 오래된 백업 연결로 되살리지 않는다. 같은 버전의 다른 내용은 충돌이며, 문제나 기록의 ID·원래 응답 시각을 새로 만들지 않는다.

`OriginalRepository.save`는 원문 상태와 해당 변경의 outbox를 같은 IndexedDB readwrite transaction에 쓴다. 둘 중 어느 put이라도 실패하면 전체 transaction을 abort한다. 계정 저장소에도 같은 원칙을 적용한다.

- 원문 `generation`: 이 기기의 상태 저장 충돌 검사. 전 기기 서버 버전이 아니다.
- 동기화 메타데이터 `revision`: 커서·수신 확인 등 메타데이터 저장의 별도 충돌 검사.
- 상태가 바뀌지 않은 수신 확인은 답안 저장의 generation을 불필요하게 증가시키지 않는다.
- 서버 수신 확인 전에는 outbox를 지우지 않는다. 서버가 받은 뒤 로컬 확인 저장에 실패해도 같은 eventId를 재시도한다.
- 로그아웃하면 개인 화면·인증 캐시를 닫는다. 이전 계정의 문제·진행 답안·outbox는 그 계정 키에 남고 다른 계정으로 전송되지 않는다. 진행 중 학습을 종료하고, 필요하면 전체 백업과 동기화 복구 파일을 내보낸다.

## 이벤트와 서버 RPC

구현 위치:

- `src/original/sync/types.ts`: 이벤트·응답 순서·projection 타입
- `src/original/sync/protocol.ts`: 순수 생성·병합·충돌 처리
- `src/original/sync/local.ts`: 계정별 IndexedDB 상태·outbox
- `src/original/sync/transport.ts`: Supabase Auth/Storage/RPC 통신과 해시 검증
- `src/original/sync/controller.ts`: 재시도·페이지 회수·계정 연결·해결 동작
- `supabase/migrations/202610230001_original_sync.sql`: 테이블·RLS·버전 RPC·비공개 객체 정책
- `supabase/rls-tests.sql`: 독립 테스트 DB에서 실행할 실제 SQL 정책 검증

공통 식별 정보는 `protocolVersion=1`, `eventId`, `deviceId`, `deviceSequence`, `baseCursor`, `createdAt`이다. `eventId`는 재시도 중 바뀌지 않는다. `deviceSequence`는 기기 내 원래 저장 순서이며 로컬 응답에도 먼저 할당한다.

| kind | 논리 내용 |
|---|---|
| `bank` | 읽은 서버 `baseVersion`, 새 문제은행, 삭제 표시·질문/파일 tombstone, 명시적 재등록 ID |
| `session` | 완료·종료 세션, 그 세션의 확정 Attempt 전체, 원래 기기별 응답 순서 |
| `mark` | 문항 ID, `value=true/false`, 읽은 `baseMarkVersion` |
| `resolution` | 문제·채점 버전, 실제 후보 Attempt ID 목록과 사용자가 선택한 대표 Attempt ID |

논리 이벤트는 검증 후 메모리에서 사용한다. 서버 이벤트 행에는 큰 그림을 반복해서 넣지 않고 비공개 객체 manifest의 경로·SHA-256·크기를 둔다. 본문과 그림은 작은 조각으로 전송한다. 그림은 내용 해시로 재사용하며, 수신 시 조각 크기·각 해시·합쳐진 그림 해시·자산 참조를 확인한 뒤 기존 원문 검증을 통과시킨다. 완전히 내려받고 검증한 자료만 기존 정상 자료 대신 반영한다. 만료되는 서명 URL을 문항 ID로 저장하지 않는다.

RPC 계약:

```text
police_sync_push(p_event: WireEvent)
  -> { seq, bankVersion, markVersion, duplicate, serverTime }

police_sync_pull(p_after: bigint, p_limit: 1..100)
  -> { events: [{ seq, bankVersion, markVersion, event: WireEvent }],
       cursor, bankVersion, serverTime }
```

Storage manifest를 먼저 올린 다음 push한다. 서버는 호출한 `auth.uid()`와 객체의 첫 경로 조각이 같은지 검사한다. 사용자가 보낸 userId를 소유권으로 사용하지 않는다. pull은 계정 안의 서버 seq 순서로 페이지를 반환하며, 반환한 마지막 이벤트까지만 cursor를 이동한다. 실시간 연결에 의존하지 않고 재접속 시 cursor 이후를 다시 회수한다.

한 Storage 객체와 RPC가 가리키는 manifest의 최대 크기는 1 MiB다. 더 큰 본문·그림은 이보다 작은 조각으로 나누므로 전체 문제은행을 이 제한에 억지로 맞춰 잘라내지 않는다. SQL Editor에서 migration을 다시 실행해도 이 앱이 만든 18개 정책만 교체하고 다른 정책·기존 행은 유지하도록 transaction 안에서 처리한다.

서버 테이블:

| 테이블 | 역할 |
|---|---|
| `police_sync_heads` | 사용자별 cursor와 문제은행 CAS 버전. 사용자 행을 잠가 변경 직렬화 |
| `police_sync_events` | `(user_id,event_id)`, `(user_id,device_id,device_sequence)`, `(user_id,seq)` 고유 제약을 가진 이벤트 로그 |
| `police_sync_marks` | 사용자·문항별 최신 표시 변경 버전. 해제도 남김 |

같은 eventId·같은 wire 내용은 같은 수신 확인을 반환한다. 같은 eventId의 다른 내용은 충돌이다. 은행의 baseVersion 또는 표시 baseMarkVersion이 오래되면 서버가 거부한다. 클라이언트가 재접속했다고 오래된 변경의 버전을 자동으로 새 값으로 바꾸지 않는다. 사용자가 최신 자료와 보관된 변경을 확인한 뒤 명시적으로 다시 반영한다.

## 응답 순서와 보류 K

서버 도착 시각을 원래 `answeredAt`으로 덮지 않는다. 단순히 받은 배열을 끝에 붙여 과거 오답을 최근 정답으로 만들지 않는다.

1. 같은 기기에서는 `deviceSequence`로 원래 확정 순서를 보존한다. 시각이 같거나 기기 시계가 뒤로 가도 이 순서가 우선한다.
2. 다른 기기의 이벤트를 본 뒤 만든 응답은 `baseCursor`와 해당 이벤트의 서버 seq로 인과 순서를 확인한다.
3. 인과 관계가 없는 다른 기기 응답은 보존된 시각과 유효한 시계 보정의 불확실성 구간을 비교한다. 구간이 분리되면 순서를 정한다.
4. 보정이 없거나 구간이 겹치면 자동 대표 상태를 고르지 않고 해당 문제를 K로 보류한다. 서로 다른 기기의 기록을 지우거나 정답인 쪽을 자동 선택하지 않는다.

시계 보정은 서버 응답과 클라이언트 왕복 구간으로 측정한다. 런타임 ID와 `performance.now()` 기준점도 함께 기록한다. 앱을 재시작하여 런타임이 달라졌거나 Date 경과와 단조 시계 경과가 2초 넘게 다르면 해당 보정을 사용하지 않는다. 보정 시각에서 24시간 넘게 떨어진 응답에도 오래된 보정을 사용하지 않으며, 경과 시간의 0.1%를 추가 불확실성으로 적용한다. 이 수치는 보수적인 제품 정책이며 기기 시계 정확도 보증이 아니다. 런타임에서 시계를 신뢰할 수 없으면 보정을 null로 두어 확인을 요청한다.

순수 병합은 기기 내 순서·관찰한 서버 이벤트의 인과 관계로 순서 그래프를 만들고, 시각·기기 ID·저장 순서·Attempt ID를 고정된 동률 규칙으로 사용한다. 같은 입력 집합은 도착 순서와 관계없이 수렴한다. 미확정 교차 기기 순서가 대표 상태에 미치는 영향은 K로 분리한다.

확정 대표가 없는 문제도 현재 출제 가능한 등록 문항 N에는 남긴다.

```text
N = C + W + U + M + K
A = C + W + U
B = C + W
풀이율 = A / N
오답률 = W / B  (B=0이면 —)
미해결률 = (W+U) / A  (A=0이면 —)
```

K는 미풀이 M이나 오답 W로 세지 않는다. 단원 오답률·반복 오답·추천의 확정 수치에서 잠시 제외하고 별도로 표시한다. 공란은 계속 유효 응답에서 제외한다. 이전 gradingRevision의 기록도 현재 대표 상태로 사용하지 않는다.

계정·기기 동기화 화면에서 사용자가 실제 후보 기록 중 대표 상태를 선택하면 resolution 이벤트를 동기화한다. 원래 Attempt 둘은 보존한다. 후보 집합이 나중에 달라지면 과거 해결을 새로운 응답에 자동 적용하지 않는다. 같은 기기의 진행 중 확정 응답은 다른 기기로 보내기 전에도 현재 기기의 대표 상태 계산에 사용한다.

## 원격 자료와 진행 중 학습

완료 세션은 세션/Attempt/문항·그림 스냅샷의 한 묶음이다. 부분 묶음이나 같은 ID의 다른 내용은 정상 기록으로 덮어쓰지 않고 원본 이벤트와 함께 충돌로 보관한다. 문제은행보다 새로운 풀이 스냅샷은 새 은행 수신까지 보류하고 수신 확인 완료로 처리하지 않는다. 해당 은행이 준비되면 보류 묶음을 다시 검증한다. 은행보다 먼저 도착한 역사 문항은 새 출제 대상으로 승격하지 않으며, 필요한 그림과 스냅샷 참조를 함께 보존한다.

진행 중 세션이 있으면 원격 은행과 완료 기록을 durable deferred 목록에 보관한다. 활성 세션·임시 답안·종료 시각은 유지한다. 종료 뒤 내려받은 자료를 검증하여 원자적으로 반영한다. 그림이나 문제은행을 못 받았다는 이유로 현재 정상 자료를 지우지 않는다.

문제은행 내용 충돌을 보류해도 수신한 서버 CAS 버전은 기억한다. 그렇지 않으면 이후 이벤트와 사용자의 명시적 병합이 영구적으로 오래된 버전에 막힐 수 있다. 보류된 원격 내용은 충돌 이벤트에 남고, 최신 서버 은행과 로컬 변경을 합쳐 확인한 뒤 재전송한다.

삭제된 원문이 과거 세션에 필요하면 역사 스냅샷과 참조를 보존하되 새 출제 모집단에서는 제외한다. 파일을 지운 기기의 오래된 오프라인 은행이 나중에 전송되어도 서버 CAS가 거부하고 tombstone을 유지한다. 의도적 재등록은 최신 버전을 읽은 별도 변경으로 처리한다.

## 인증·RLS·비공개 객체

브라우저에는 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`만 사용한다. 관리자 secret/service_role/DB 비밀번호를 프런트 환경변수나 저장소에 넣지 않는다.

테이블에는 user_id 소유권 RLS가 있으며 클라이언트의 직접 INSERT/UPDATE/DELETE 권한은 부여하지 않는다. 변경은 인증된 RPC만 수행한다. RPC는 `SECURITY DEFINER`, 빈 search_path, 명시적으로 한정한 테이블 이름을 쓰며 호출자의 auth.uid()를 검사한다. 익명 RPC 실행 권한은 없다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Database functions](https://supabase.com/docs/guides/database/functions) 기준을 참고했다.

`police-sync-private` 버킷은 비공개다. 경로는 `<인증 사용자 UUID>/real/...`이며 다른 계정·익명 요청을 제한한다. 기존 프로젝트에 넓은 permissive Storage 정책이 있어도 이 버킷에는 restrictive 소유권 방어를 추가한다. 앱에서 올린 내용 주소 객체는 덮어쓰거나 삭제하지 않는다. [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control) 방식에 따른다.

로그인·API 응답과 개인 자료는 공용 service worker 캐시에 넣지 않는다. PWA의 정적 앱 캐시와 개인 IndexedDB 데이터는 별도다. 앱 재실행 시 outbox를 재시도하며 브라우저가 닫힌 동안의 백그라운드 전송을 보장하지 않는다.

## 오류와 복구

- **이 기기에 저장됨**: 로컬 transaction 완료. 서버 수신 성공과 구분한다.
- **오프라인·전송 대기 n건**: outbox 유지. 다시 앱을 열거나 네트워크가 돌아오면 재시도한다.
- **원격 자료 대기**: 현재 학습을 마친 뒤 검증·반영한다.
- **응답 순서 확인 필요**: K 후보 중 실제 대표 기록을 선택한다.
- **버전 충돌**: 최신 자료와 남은 변경을 확인한 뒤 명시적으로 반영한다. 오래된 삭제·중요 표시를 자동 재전송하지 않는다.
- **저장/다운로드 실패**: 기존 정상 자료와 기록을 유지한다. 전체 백업 및 동기화 대기열·충돌 복구 파일을 내보낼 수 있다.

전체 원문/OX 백업, 문제만 내보내기, 동기화 대기열·충돌 복구 파일은 서로 목적이 다르다. 계정 연결에 사용한 원본 전체 백업은 로컬에서 다시 내보낼 수 있으며 OX를 공개 클라우드 자료로 올리지 않는다. 로그인한 계정의 기존 백업 연결은 전체 교체 복원이 아닌 검증된 병합으로 처리한다.

## 검증 결과와 실서비스에서 남은 확인

OX 확장과 현재 검증 결과는 [OX 동기화](OX_CLOUD_SYNC.md), [추가 검증 기록](OX_IMPLEMENTATION_VERIFICATION.md)을 따른다. 아래 원문 최초 구현 시점의 기록과 구분한다.

최종 단위·통합 테스트는 전체 275개이며, 여기에 순수 프로토콜 42개와 fake-indexeddb 저장 통합 11개가 포함된다. 해당 대상 실행이 통과했다. 프로토콜 재시도·같은 ID 충돌·두 기기 완료 세션·늦은 오래된 응답·K 해결·삭제/해제·활성 세션 보류·은행 의존 묶음 재처리·역사 그림의 정확한 참조 검증과, 상태/outbox 양쪽 put 실패 rollback·계정/OX/demo 분리·로그아웃 보존·오래된 표시 폐기를 검사한다. 전체 프로젝트 빌드·회귀·브라우저 결과는 `IMPLEMENTATION_VERIFICATION.md`와 최종 실행 보고를 따른다.

이 환경에는 Supabase 프로젝트 URL·publishable key·이메일 설정과 실행 가능한 PostgreSQL/Supabase CLI가 제공되지 않았다. 따라서 실제 이메일 인증, 두 실제 기기의 원격 수렴, 운영 RLS 실행을 통과했다고 보고하지 않는다. `supabase/rls-tests.sql`은 준비된 24개 pgTAP 검사이며 아직 실행하지 않았다.

실서비스 연결 후 격리된 테스트 프로젝트에서 다음 순서로 확인한다.

1. SQL migration을 적용하고 `supabase test db supabase/rls-tests.sql` 또는 테스트 DB 소유자의 psql로 RLS 스크립트를 실행한다. 테스트에는 두 가상 auth.users와 Storage 메타데이터를 만들고 끝에 rollback한다.
2. 실제 Storage 업로드/인증 다운로드와 해시 검증을 확인한다. SQL 메타데이터 검사만으로 객체 바이트 접근을 검증했다고 간주하지 않는다.
3. 이메일 OTP 템플릿·만료·요청 제한과 두 테스트 계정의 인증을 확인한다.
4. 저장소가 분리된 두 브라우저 context로 로그인·완료 세션·오프라인·응답 유실 재시도·다른 계정 거부를 확인한다.
5. 같은 계정의 PC와 갤탭에서 학습 현황과 K 해결이 수렴하는지 확인한다. 실제 갤탭이 없으면 viewport 자동화와 실기기 미검증을 구분한다.

배포와 이전 절차는 `WEB_DEPLOYMENT.md`, `PC_TO_TABLET_MIGRATION.md`를 함께 따른다.
